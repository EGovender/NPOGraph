# Roadmap

This is a living plan, not a commitment with dates. Phases are ordered by dependency — each one assumes the previous is stable enough to build on — not by a fixed timeline.

## Phase 0 — Vision and core concepts (current)

- [x] Vision and guiding principles
- [x] First-draft core concepts (~40, grantmaking only)
- [x] First-draft relationships and lifecycle
- [x] Business rules documented in detail, separate from relationships — see [Properties & Rules](06-properties-and-rules.md) and `ontology/source/business-rules.json`
- [ ] Event model (what state transitions fire, e.g. "Award Approved", "Payment Released")
- [ ] Governance: how concept proposals are reviewed and accepted, and by whom

## Phase 1 — Machine-readable ontology

- [x] Canonical JSON representation of concepts and relationships (`ontology/source/*.json`)
- [x] JSON-LD context and graph (`ontology/context.jsonld`, `ontology/npograph.jsonld`)
- [x] OWL ontology (`ontology/npograph.ttl`)
- [x] RDF export (`ontology/npograph.rdf`, `ontology/npograph.nt`)
- [x] SHACL shapes for structural validation (`ontology/npograph.shapes.ttl`)
- [x] A documented process for keeping formats in sync with the docs — see [Data Model](05-data-model.md); enforced in CI via `.github/workflows/ontology.yml`
- [x] Concept attributes (`owl:DatatypeProperty`) and per-concept SHACL property shapes (required-ness, datatype, allowed values) — see [Properties & Rules](06-properties-and-rules.md), `ontology/source/properties.json`, `ontology/npograph.property-shapes.ttl`
- [ ] SHACL/other validation of state-transition business rules once an event model exists (see Phase 0)

## Phase 2 — Interactive explorer

- [x] A static site (Astro + React, on GitHub Pages) that renders the concepts and relationships as a browsable, linked knowledge graph — see `site/`, live at [egovender.github.io/NPOGraph](https://egovender.github.io/NPOGraph/)
- [x] One page per concept, generated from the same source as the docs (`site/src/pages/concepts/[id].astro`, reading `ontology/source/*.json`)
- [x] Basic keyword search over concept names, aliases, and definitions (`site/src/components/SearchBox.tsx`)
- [x] Property inspector (Overview / Properties / Relationships / Rules / Technical tabs) on both the concept page and the explorer's node detail panel — see `site/src/components/PropertyInspector.tsx`, styled after Neo4j Bloom's inspector + graph controls (zoom/fit), aiming for a friendlier feel than Bloom's
- [ ] Known gap: a handful of concepts (`indirect-cost-rate`, and the `evaluation`/`output`/`outcome` trio) have no documented relationships yet, so they appear disconnected in the graph explorer — that's an honest reflection of the current ontology, not a site bug. Worth revisiting when Phase 0's business-rules/event-model work happens.

## Phase 3 — Learning and design tools

- [x] Most of "Learn" mode landed early via the Phase 2 property inspector: purpose (Overview tab), business rules (Rules tab), and lifecycle position (Properties tab's Lifecycle group) are already on every concept page
- [x] Worked examples per concept and the end-to-end "story mode" walkthrough turned out to be one dataset viewed two ways — see [Worked Example](07-worked-example.md): a single fictional grant (`ontology/source/example.json`) generated as real, SHACL-validated `owl:NamedIndividual`s (`ontology/npograph.example.ttl`/`.jsonld`), surfaced as an Example tab on the concepts it touches and as the full sequence at `site/src/pages/story.astro`
- [x] "Design" mode: a hybrid question set (`site/src/data/design-questions.ts`) — mostly independent yes/no toggles, plus a few `showIf`-gated follow-ups and one single-select branch where a real dependency exists — recommending a live-updating concept subset at `site/src/pages/design.astro`

## Phase 3.5 — Organizational foundation

Prompted by a gap the grantmaking-only model couldn't express: an organization like a philanthropic intermediary can simultaneously be a grantmaker, a fiscal sponsor, a DAF sponsor, and a grantee/subrecipient — not one of these permanently, but each contextually, engagement by engagement. See [Organizations, Roles & Arrangements](08-organizations-roles-and-arrangements.md) for the full design.

- [x] **Milestone 1 (this phase):** `Funder`, `Grantee`, and `Fiscal Sponsor` reparented from `Organization` subtypes to `Organization Role` subtypes, with role occupancy reified (`Organization --playsRole--> Organization Role --appliesWithin--> Philanthropic Arrangement`) so the same organization can hold multiple, independently-dated roles. Added `Organization Role`, `Organization Type`, `Philanthropic Intermediary`, `Funding Intermediary Role`, `Fund`, and `Philanthropic Arrangement` (48 concepts total), plus direct `Award` party edges (`awardedBy`/`awardedTo`/`fundedFrom`/`managedBy`) so intermediary philanthropy can name different organizations for each.
- [x] **Milestone 2 — Intermediary philanthropy:** concrete arrangement subtypes (`Fiscal Sponsorship Arrangement`, `Donor-Advised Fund Arrangement`, `Regranting Arrangement`, `Collaborative Fund Arrangement`) as `subClassOf philanthropic-arrangement`; `Donor-Advised Fund` as a `Fund` subtype; `Sponsored Project`; `Grant Recommendation`; `Donor Advisor` (56 concepts total). See [Organizations, Roles & Arrangements](08-organizations-roles-and-arrangements.md#milestone-2-intermediary-philanthropy) for two scope refinements made during implementation: no separate "Sponsored Project Arrangement" or "Funding Intermediary Arrangement" (each would duplicate an existing concept), and `Donor Advisor` modeled as a person-level concept rather than an `Organization Role` subtype.
- [x] **Milestone 3 — Second worked example + explorer views:** a second, connected thread in the worked example where Ocean Conservation Fund — already the Funder in the direct-grant thread — also plays a Fiscal Sponsor role for a Sponsored Project in a separately-dated arrangement, the first instance data for `Organization`, dated `Organization Role` occupancy, `Fund`, and `Philanthropic Arrangement`; an explorer view selector (grant lifecycle / organizations & roles / funds & arrangements / full ontology); visual node-shape differentiation by concept kind. Found and fixed a second inheritance gap along the way (relationship validation and the site's Relationships tab weren't subclass-aware, mirroring Milestone 1's SHACL/properties fix) — see [Organizations, Roles & Arrangements](08-organizations-roles-and-arrangements.md#milestone-3-instance-data-and-explorer-views) for why that fix satisfied the planned "per-type inspector tab variants" without needing bespoke tabs.
- [ ] **Milestone 4 — Enterprise architecture layer:** Business Capability, Business Process, Application System, Data Object, Integration, Policy, Organizational Unit — explicitly not started; only after the philanthropic structure above has had real use.

## Phase 3.6 — Product alpha readiness

Prompted by an external implementation-plan review (a 10-milestone product plan for turning NPOGraph into a trustworthy, usable alpha) that was reconciled against actual repo state before being adopted here — several of its concerns (deployment/source sync, contribution governance process, 4 of its proposed graph views) turned out to already be solid; the milestones below are the reconciled, genuinely-remaining work, roughly in dependency order.

- [x] **Milestone 1 — Site trust & positioning:** build-time-computed ontology version/last-updated display (homepage and footer, sourced from git history rather than hand-maintained, so it can't drift the way `meta.json`'s version previously did); a homepage rewrite (problem statement, audience, real CTA buttons, live concept/relationship counts); navigation active-page state, a mobile menu, and targeted renames (`Explore`→`Graph`, `Design`→`Model Your Program`, `Story`→`Worked Example`); Open Graph/Twitter Card/canonical meta tags and a generated social-preview image; a deployment verification checklist ([Deployment Checklist](09-deployment-checklist.md)).
- [x] **Milestone 2 — Concept catalogue:** live search (sharing the homepage search box's relevance scoring, factored into `site/src/data/search.ts`), category and "has example/properties/relationships/business rules" filters, a category/alphabetical sort toggle, aliases and "Specializes X" indicators surfaced directly on `/concepts` cards, live per-group and total counts, an empty state, and URL-persisted filter state (`?q=&cat=&has=&sort=`). Built as progressive enhancement — the full, ungrouped concept list is in the static HTML either way, so search engines and no-JS users still see everything; a "status" filter from the original plan is deferred to Milestone 7, which is what actually adds a concept-level maturity field.
- [x] **Milestone 3 — Graph exploration, part 2:** in-graph search (sharing the same relevance scoring as the homepage and catalogue), a deterministic/stable cose layout (seeded with fixed starting positions instead of `randomize: true`, verified byte-identical node positions across repeated loads), BFS path-finding between two concepts (treating relationships and subclass edges as undirected, with the path highlighted on the graph and listed as a breadcrumb), URL-persisted view/concept/search state (`?view=&concept=&q=`), PNG export, a fullscreen toggle, and a keyboard-accessible list alternative (every visible concept and relationship as plain, screen-reader-navigable HTML, toggled in place of the canvas). (4 views and node-shape differentiation shipped in Phase 3.5 Milestone 3 — this was the remaining slice.)
- [x] **Milestone 4 — Philanthropic intermediary model, remaining slice:** three more worked-example threads — a Donor-Advised Fund, a Regranting Arrangement (giving Ocean Conservation Fund a fourth independently-dated role, Funding Intermediary), and a Collaborative Fund Arrangement between two other organizations — bringing every Phase 3.5 arrangement subtype to real instance data; a Mermaid role-change diagram in `docs/08`; and a `legalNote` field on the 8 concepts with real legal/regulatory nuance this ontology deliberately simplifies (Fiscal Sponsor, Sponsored Project, Fiscal Sponsorship Arrangement, Donor Advisor, Donor-Advised Fund, Donor-Advised Fund Arrangement, Grant Recommendation, Regranting Arrangement), rendered as a callout on the concept page and a badge on its catalogue card.
- [x] **Milestone 5 — Design tool expansion:** questions grouped into five labeled sections (Organization & operating model, Funding structure, Application & review, Awards & payments, Compliance/reporting/outcomes) with a per-section progress count; seven new questions covering every Phase 3.5 arrangement type and multi-role organizations (up from one question touching this layer, which only ever added `Fiscal Sponsor`); per-question `help` text now rendered (previously modeled in the data but never shown); export to JSON, JSON-LD, and Markdown; a shareable URL (`?loi=yes&review=yes&...`, one param per question); and "open in graph," which added a new ad-hoc `?concepts=` mode to the explorer distinct from its named views. Found and fixed two real bugs along the way: a React hydration mismatch from reading `window.location` during initial state in both this tool and the explorer (fixed by restoring URL state in a post-mount effect instead of eagerly in the initializer), and a same-commit race in the explorer where three separate effects each independently decided whether to clear the current selection based on stale closures, silently overwriting a URL-restored selection (fixed by consolidating all graph highlighting into one idempotent function).
- [x] **Milestone 6 — Story mode polish:** a scenario selector splitting the single flat timeline into "All" plus one tab per narrative thread (Direct Grant, Fiscal Sponsorship, Donor-Advised Fund, Regranting, Collaborative Fund — derived automatically from each thread's `act` marker, no hand-maintained scenario list); a sticky lifecycle-stage progress bar per scenario, scrollspy-highlighted as you scroll through that scenario's steps; and "open in graph" on every step, linking to the explorer pre-selected on that step's concept. URL-persisted scenario selection (`?scenario=`). Found and fixed two real bugs: a redundant "A" in one thread's `act` string (`ontology/source/example.json`) producing an awkward auto-derived slug/label, and a CSS specificity bug where `.story-stage-bar`/`.story-step`'s own `display: flex` rules silently overrode the browser's `[hidden] { display: none }`, so JS-toggled visibility had no effect until explicit `[hidden]` override rules were added.
- [x] **Milestone 6.5 — Graph engine migration (Cytoscape.js → D3):** rebuilt the explorer's rendering/interaction layer from scratch on `d3-force`/`d3-zoom`/`d3-drag`/`d3-shape` over a raw SVG, replacing Cytoscape.js (removed as a dependency). Same deterministic seeded-start force layout, zoom/pan, drag-to-reposition, click-to-select with the properties panel, path-find/search/selection highlighting, category filtering, PNG export, fullscreen, and the keyboard-accessible list view as before, plus new capabilities: an expanded 7-kind node taxonomy (Organization, Organization Role, Grant Program, Grant, Fund, Arrangement, Other — `site/src/data/graph-kinds.ts`) with its own filter and matching shapes, a 6-bucket relationship-type taxonomy (Structural, Organizational, Funding & program setup, Application & decision, Award/disbursement & compliance, Outcomes & closeout — `site/src/data/relationship-kinds.ts`) with its own filter, and relationship labels with directional arrowheads (shown on connection/selection or via a "show all" toggle). Also fixed two dangling-edge/rebuild gaps left over from the Cytoscape version (edges connected to a filtered-out node now hide with it; filters and highlight state now survive a view-switch rebuild) and one real timing bug found during testing: a small (e.g. mini-mode) graph's simulation can settle and fire before its embedding container's first layout pass, leaving the view permanently mis-framed — fixed with an immediate seeded-position fit plus a bounded fallback so the settled-layout fit always eventually applies.
- [ ] **Milestone 7 — Governance, versioning & testing:** a concept-level maturity field (draft/under-review/stable/deprecated) threaded through the generator, SHACL, and the site; an actual version-bump discipline for `meta.json` (it sat at one value across several milestones that added real concepts before Milestone 1 above); a first test suite (ontology integrity tests beyond SHACL shape-conformance; basic site build/rendering tests) — none exists today beyond `tools/validate_ontology.py`.
- [ ] **Milestone 8 — Accessibility, performance & SEO:** a full keyboard/screen-reader pass, Lighthouse targets, a performance budget at higher concept counts, sitemap/robots.
- [ ] **Milestone 9 — Publish `v0.1-alpha`:** release notes, changelog, a known-limitations doc, versioned artifacts, a GitHub release tag.

## Phase 3.7 — Nonprofit knowledge model & reference-data governance

Prompted by an external 37-page knowledge-model implementation plan reconciled against actual repo state before being adopted here — a structural remodel of the ontology itself (a first-class Person/Role model, a SKOS-based controlled-vocabulary framework, and a split of the overloaded Organization Type concept), closer in spirit to Phase 3.5's organizational-foundation work than to Phase 3.6's site-polish milestones. Sequenced before Phase 3.6's remaining Milestones 7-9, since those build naturally on the reference-data framework and role model this phase establishes (Milestone 7's concept-maturity field and first test suite in particular). Reconciliation found: no `Person` or shared `Role` superclass exists today (`organization-role` has exactly 4 subclasses — `funder`, `grantee`, `fiscal-sponsor`, `funding-intermediary-role` — and four flat, unrelated concepts — `program-officer`, `reviewer`, `grant-administrator`, `donor-advisor` — describe people performing functions with no shared parent); no controlled-vocabulary system exists at all (all 34 `enum` properties store inline `allowedValues` arrays with no scheme/deprecation/mapping metadata); `organization-type` combines legal and tax classification while a separate `organization-tax-status` enum property already duplicates part of it; and the just-shipped D3 graph explorer (Milestone 6.5) added a client-derived `ConceptKind` that collides in name with this plan's proposed ontology-authored `kind` field — resolved by adopting the ontology-authored field as authoritative and refactoring the explorer's derivation into a passthrough.

- [x] **Milestone 1 — Role foundation:** a shared `role` concept; a new `person` entity; `person-role` (subclassing `role`); reparented `organization-role` under `role`; reparented the 4 existing person-function concepts (`program-officer`, `reviewer`, `grant-administrator`, `donor-advisor`) to `person-role` with rewritten "the role a person occupies when..." definitions; added `employee`/`board-member`/`applicant-contact`/`authorized-signatory`/`donor`/`consultant` as new `person-role` concepts (65 concepts total, up from 56); shared role properties (`effectiveFrom`/`effectiveTo`/`status`/`scope`/`notes`) on `role`, inherited by every subclass via the existing `subClassOf` resolver and validated by SHACL; core relationships (`Person playsRole Person Role`, `Person affiliatedWith Organization`, `Person Role appliesWithin Organization`); adopted the ontology-authored `kind` field across all 65 concepts (13 values, up from the D3 explorer's 7 client-derived ones), refactoring `graph-kinds.ts` into a passthrough reading `concept.kind` directly, with new shapes for the added kinds. Deviated from the original plan in three ways found during implementation: (1) skipped `Role roleHeldBy Person|Organization` — the generator requires every relationship predicate to be globally unique, and the existing convention (`playsRole` in the holder→role direction, confirmed in both the schema and the worked example's instance data) already answers "who holds this role" without a redundant reverse edge; `Person playsRole Person Role` mirrors it instead. (2) That same uniqueness constraint meant `playsRole`/`appliesWithin` couldn't be reused verbatim for Person, so the new relationships use `personPlaysRole`/`personRoleAppliesWithin` — Milestone 2's context-model broadening will need to resolve this properly (likely a generator change to support one predicate across a union of object concepts) rather than continuing to mint per-agent-type predicate names. (3) Discovered `organization-role` already had its own `status`/`effectiveFrom`/`effectiveTo`/`scope` properties (pre-dating this milestone, with a narrower 3-value status enum) sitting alongside the new shared ones on `role` — removed the duplicates so `organization-role` inherits cleanly, which also surfaced (and required a one-line data fix for) a real SHACL-generation gap: `tools/generate_ontology.py`'s property-shapes generator was never exercised against a property declared on a shared grandparent before, though it turned out to already work correctly once the duplicate was gone, needing no generator change.
- [x] **Milestone 2 — Organization role expansion:** added `contractor`/`vendor`/`service-provider`/`employer`/`partner`/`sponsoring-organization` as `organization-role` subclasses (71 concepts total, up from 65), each definition documenting the real distinction between them rather than relying on color/shape alone (see [Organizations, Roles & Arrangements](08-organizations-roles-and-arrangements.md#phase-37-milestone-2-contractorvendorservice-providerpartner-and-the-broadened-role-context-model)); converted `role-scope` from a free-text string to an inline enum (`organization-wide`/`program-specific`/`project-specific`/`award-specific`/`agreement-specific`/`arrangement-specific`/`transaction-specific`), migrating the two existing free-text scope values into the closest enum value with the original text preserved in `notes`; a sixth worked-example thread (Tidal Marketing Collective as a Contractor to Ocean Conservation Fund, scoped directly to the Organization rather than an Arrangement) exercising both the new subclasses and the new context relationship. Deviated from the original plan by adding only one new context relationship, `Organization Role appliesWithin Organization`, instead of the full twelve-context-type `Role appliesWithin Context` union — the generator's global predicate-uniqueness constraint means a true union-typed object isn't representable without either a generator change or a blank-node-based `owl:unionOf` (ruled out by the "no blank nodes" determinism invariant), and no worked-example data yet needs the other ten context types (Award/Application/Agreement/Fund/Grant Program/Funding Opportunity/Project/Review/Payment/Decision); deferred until real instance data actually needs one, at which point the generator-level question should be revisited rather than resolved speculatively.
- [ ] **Milestone 3 — Reference-data framework:** new `ontology/source/reference-data/` directory and per-scheme JSON schema; generator changes to load/validate/generate SKOS (`skos:ConceptScheme`/`skos:Concept`, `broader`/`narrower`/`exactMatch`/`closeMatch`, `dcterms:source`) across all existing output formats; SHACL for reference-backed properties (`sh:class skos:Concept` + scheme-membership); migrate only the "Shared" vocabularies first (Role Status, Organization Operating Status, Publication Status, Frequency, Restriction Type) as the proving ground.
- [ ] **Milestone 4 — Organization classification split:** migrate `organization-type` into `legal-form`/`tax-status`/`organization-classification` as governed reference-data vocabularies (deprecate-with-replacement, not silent rename); migrate the existing `organization-tax-status` enum property to reference the new Tax Status scheme; jurisdiction metadata on tax status values; grantmaking-domain vocabularies (Application/Review/Decision/Award/Payment/Report Status, Award Type).
- [ ] **Milestone 5 — Explorer support:** a top-level "Reference Data" nav page/route; `PropertyInspector` tab variants for Role and Classification/Reference-scheme kinds (today's tab list is a static tuple, not per-kind); node shapes/behavior driven by the now-authoritative `kind` field; expanded search across reference values and codes.
- [ ] **Milestone 6 — Examples, docs & hardening:** a third worked-example thread (one person holding multiple concurrent roles); `docs/10-knowledge-model-implementation.md` and `docs/11-reference-data-and-controlled-vocabularies.md`, plus updates to `docs/02`/`03`/`05`/`06`/`07`/`08`; narrow-scope validator hardening (role-holder-type check, scheme-membership check, deprecated-value warning, effective-date-range check) — the broader first-ever test suite stays Phase 3.6 Milestone 7's job; final SHACL/build validation pass.

## Phase 4 — Semantic search and AI assistant

- [ ] Semantic (not just keyword) search over the ontology
- [ ] An assistant that reasons over the ontology's actual relationships (e.g., "what depends on reports?") rather than general-purpose chat

## Phase 5 — Extension beyond grantmaking

- [ ] A defined pattern for extending the core ontology into adjacent domains (fundraising, CRM, finance, programs, volunteers) as separate modules
- [ ] At least one additional domain module built out as a proof of the extension pattern

## Explicitly out of scope for now

- Building a grants-management product or any end-user application beyond the explorer
- Committing to any specific tech stack for phases 2+ before phase 0/1 are stable
- Any AI-agent code-generation capability (auto-generating APIs/schemas from the ontology) — interesting long-term, not a near-term goal
